# 有组合性的异步资源框架

来源：[Unity3D-有组合性的异步资源框架](https://zhuanlan.zhihu.com/p/8562870010)（李泉龙，编辑于 2026-10-02）。

本文把原文整理成可实现的设计说明。原文绝大部分已经反复推敲，作为本框架的设计依据。

第 1–14 节是问题域，取自原文。第 15 节是据此定下的实现规则，其中涉及流程的几条尚不稳定，后续可能调整。

## 1. 要解决的问题

游戏里的资源管理要同时处理加载、使用、缓存和卸载，并屏蔽资源种类、平台、同步/异步加载方式的差异。异步场景下有两个必须同时解决的问题：

1. **组合使用带来的状态爆炸。** 多个异步任务交错执行，资源树又可以动态增删和递归嵌套，状态数量会随节点和需求变化快速膨胀。
2. **用引用计数精确且自动地管理资源生命期。** 计数的含义是「同一时刻需要这份资源的多份逻辑拷贝」，拷贝方式可以是整份、部分或地址。

框架的组合性来自一次拆分：逻辑需求的变更是同步、确定的；只有原始资源到达是异步的。需求记在数据抽象上，原始资源到达后按固定流程刷新整棵资源树。上层不再把「这段资源该怎么处理」交给一个一次性 callback。

协程、`async` / `await` 只改变书写形式，不提供这种组合性。本框架不把它们当作资源组合的手段。

## 2. 三类资源需求

上层对资源的需求只有三类，框架的类型结构与此对应：


| 需求                       | 抽象                                    |
| ------------------------ | ------------------------------------- |
| 使用单个资源                   | `Resource` 的叶子实现，例如 `AsyncGameObject` |
| 使用一组资源，并且这组资源可以动态增删、递归嵌套 | `ResourceGroup : Resource`            |
| 对资源做引用计数                 | `Clone` / `Reference`，引用即拷贝           |


`Resource` 是统一抽象。它既可以是单个资源，也可以是成组资源，也可以是成组资源递归嵌套成的树。成组资源作为一个整体，与单个资源遵守同一套使用方式。

## 3. 核心类型

```csharp
abstract class Resource
{
    protected object data; // 资源的全部使用信息，即数据抽象
    protected object raw;  // 当前持有的原始资源

    public void SetData(object data);      // 设置使用信息
    public void SetActive(bool on);        // 使用 / 不使用
    public void ReplaceRaw(object newRaw); // 替换原始资源

    protected abstract void Load(Action<object> onLoadDone);
    protected abstract void BreakLoad();                 // 打断正在进行的加载
    protected abstract void Free(object raw);
    protected abstract void OnActive(object raw, bool active);
    protected abstract void Render(object data, object raw); // 按数据抽象修改原始资源
}
```

`data` 与 `raw` 分离是整个框架的核心。`Resource` 对象自己的存续，和它里面那份 `raw` 的生命期，是两件事。一个 `Resource` 活着的期间可以多次更换 `raw`。

`Load` 上的 `onLoadDone` 只表示「原始资源到达」。它触发整树刷新，不承载上层业务对资源的处理流程。

## 4. 数据抽象：资源的逻辑镜像

加载时机和使用需求的变化是并发的。资源还没加载上来时，使用需求已经发生，这是常态。

做法是给资源一个逻辑镜像。典型例子：角色模型加载完成前，先放一个空物体；服务器推动位置时改这个空物体，模型到达后再把位置应用到模型上。

推广之后，镜像就是该资源的**全部使用信息**，记为 `data`。任何时刻，无论 `raw` 是否已经到达，使用都分成两步：

1. 修改数据抽象（`SetData`，以及对树结构的增删）。
2. 若当前有可用的 `raw`，按数据抽象修改它（`Render`）。

```csharp
Resource r = new ConcreteResource();
r.SetData(data1);
r.SetActive(true);
// raw 可能此时尚未到达；到达后按当时的 data 刷新
r.SetData(data2);
r.SetActive(true);
```

约定：

- `data` 覆盖这份资源的全部使用信息。刷新时只读 `data`，不依赖历史上某次调用残留的参数。
- `data` 可以拆成多个字段，例如 `Vector3 position` 与 `Color color`。
- `data` 不必与 `raw` 的成员一一对应。`raw` 是 `GameObject` 时，`data` 可以是配置表的一行，而不必是位移、旋转和缩放。保存什么由上层应用决定。
- 单个资源的 `data` 容易识别。扩展到资源树之后，整棵树的数据抽象散落在各个节点里，还要包含树的结构。实现和阅读时都要把这些字段认出来。
- 从单个资源扩展到树时，镜像也是一棵树：每个节点有自己的使用信息，树本身还有结构信息。

两步修改同时覆盖同步加载和异步加载，因此两种方式可以混合，也可以切换。同步加载只是 `Load` 在返回前就交出 `raw`，随后仍走同一条 `OnActive` + `Render` 路径。同步场景下这两步比直接改物体更绕，这是为了异步组合付出的结构成本。

## 5. 单个资源的生命期

生命期属于 `Resource` 里面的 `raw`。外界把一份 `raw` 交给 `Resource`，生命期开始；`Resource` 把这份 `raw` 还回去，生命期结束。

一次完整使用：

1. 第一次 `SetActive(true)` 触发 `Load`。
2. 加载完成，生命期开始，初始化：`OnActive(raw, true)`。
3. 按当前数据抽象修改资源：`Render(data, raw)`。
4. `SetActive(false)` 结束生命期：`OnActive(raw, false)`，然后 `Free(raw)`。若加载尚未完成，同一次关闭会 `BreakLoad`。

生命期三个阶段对 `raw` 的动作：


| 阶段  | 动作                                                    |
| --- | ----------------------------------------------------- |
| 开始  | 初始化。整个生命期内不变的修改放在这里，例如把 `localScale` 设为 `Vector3.one` |
| 期间  | 按 `data` 修改、使用（`Render`）                              |
| 结束  | 复原，把开始时做的联系和改动退回去                                     |


不变的修改也可以不放进初始化，而在每次 `Render` 里重设。两种做法都允许，同一类资源里选定一种。

`SetData` 在 `raw` 尚未到达时只改镜像。`raw` 到达或被替换之后，用当时的 `data` 做 `Render`，因此中间错过的那些 `SetData` 不需要排队回放。

## 6. 加载与释放的泛化

`Load` 和 `Free` 由派生类实现，含义比「从磁盘读一个 Asset」更宽。`raw` 可以来自：

- 操作系统或引擎底层加载；
- 网络数据反序列化；
- 缓存池复用；
- 从已有资源拷贝（整份、部分或引用）；
- 已有资源的子资源、子物体。

`Free` 与 `Load` 对称：销毁、归还对象池、释放引用、解除对父资源的占用，都是 `Free`。

`ResourceGroup` 的「加载完成」不是它自己读出一个文件，而是每个子资源都已加载完成。

## 7. 打断加载

异步加载必须能打断，只有 `Load` / `Free` 是不完备的。

`BreakLoad` 终止正在进行的加载流程，例如停掉加载协程或线程。尚未开始或已经完成时，它什么都不做。

`SetActive(false)` 会触发 `BreakLoad`。此后迟到的加载完成不得再把 `raw` 交给这个 `Resource`。底层如果无法从系统层面取消 IO，完成回调里也要丢掉这份结果，不能进入 `OnActive(true)`。

## 8. 替换原始资源

使用过程中必须允许用新的 `raw` 换掉旧的 `raw`。例如正在使用一个红色篮球（`0x1234`），可以换成另一个篮球（`0x5678`）：旧对象生命期结束，新对象生命期开始，并按当前使用信息染成红色。

这个替换是单资源走向资源树的关键。上层每次使用，底层都可以用一份新的 `raw` 换上，从而容纳「逻辑上已经换成新部件，旧部件仍暂留」的状态。

```csharp
public void ReplaceRaw(object newRaw)
{
    var oldRaw = this.raw;
    if (oldRaw == newRaw) return; // 跳过同一份资源；去掉这行，流程仍应正确
    if (oldRaw != null)
        OnActive(oldRaw, false);  // 结束旧 raw 的生命期
    this.raw = null;
    if (newRaw != null)
        OnActive(newRaw, true);   // 开始新 raw 的生命期
    this.raw = newRaw;
}
```

加载完成把 `raw` 交给 `Resource`，走的就是这条替换路径：无旧对象时只开始新生命期，有旧对象时先结束再开始。

新 `raw` 开始生命期之后，要用**当前**的 `data` 做一次 `Render`。篮球例子里的「染成红色」就是这次 `Render`，而不是写死在 `OnActive` 里的颜色。原文的 `ReplaceRaw` 片段只写出了生命期切换，`Render` 由生命期流程接上，见第 15 节。

## 9. 引用即拷贝

引用计数表示：同一时刻要使用一份资源的多份逻辑拷贝。拷贝方式随资源而不同。


| 场景                                 | 实际拷贝                       |
| ---------------------------------- | -------------------------- |
| 对 prefab asset 计数                  | 把 prefab 完整实例化成 GameObject |
| 对 texture asset 计数                 | 拷贝 texture 的地址             |
| 因使用 bundle 中的某个 asset 而给 bundle 计数 | 拷贝 bundle 的一部分             |
| bundle 之间的依赖                       | 拷贝 bundle 的地址              |


思想实验：texture 或 bundle 也可以整份拷贝，系统语义仍然成立，只是多占内存。实现选择地址拷贝或部分拷贝，是性能决定，不是另一套生命期。

```csharp
class Resource
{
    protected HashSet<Clone> clones; // 以本资源为模板的全部拷贝
}

class Clone : Resource
{
    public Clone(Resource template);
}

class Reference : Clone
{
    // 传统引用计数：只拷贝模板的地址
}
```

约定：

- 被拷贝的一方是模板。模板与拷贝成对出现。拷贝方式是抽象的，不同资源有不同实现。
- 存活 `Clone` 的集合就是计数。没有存活拷贝时，模板不再被使用，可以释放。
- `Clone` 自己也是 `Resource`，还可以再被拷贝。容器 UI 的 Item 从 prefab 实例化出来，这个 Item 还可以再拷贝多份。一份资源可以既是拷贝，又是别人的模板。
- `Reference` 是 `Clone` 的派生类，对应传统的「只增加一次地址引用」。

## 10. 成组资源

一组资源必须全部加载上来，才能一起使用。`ResourceGroup` 是 `Resource` 的派生类：对外仍是一份资源，对内要协调多个子资源，状态比叶子复杂。

```csharp
class ResourceGroup : Resource
{
    protected HashSet<Resource> children; // 逻辑上的子资源，与 raw 是否到达无关

    public void AddChild(Resource child);
    public void RemoveChild(Resource child, bool destroyAfterRemove = true);
}
```

角色模型由骨骼、头、上身、下身、鞋子、背饰等部件拼成，运行中可以替换其中一个、多个或全部。翅膀部件本身又可以由左翼、右翼和特效拼成。

### 10.1 动态增删

无论成组资源的 `raw` 处于什么状态，都可以增删子资源。`children` 记录的是逻辑构成，不依赖子资源是否已经加载。

成组资源的生命期开始时，初始化子资源之间的联系；结束时把这些联系复原。

### 10.2 包含即引用

子资源可能同时属于多个成组资源，因此成组资源持有的是子资源的引用，而不是独占子资源。

```csharp
class ResourceGroup : Resource
{
    public void AddChild(Resource newChild)
    {
        // ...
        var reference = new Reference(newChild);
        children.Add(reference); // 持有子资源的引用
        // ...
    }
}
```

增删子资源会改掉「当前这一组」这个整体：

1. 用新的一批子资源 `Reference` 替换本节点的数据抽象。
2. 递归向上，替换每一级父资源的数据抽象。

旧的整体不再是逻辑需求。父节点若仍握着旧整体，树的镜像就分裂了，所以替换必须走到根。

`AddChild` 时做循环引用检查，拒绝「父包含子，子又包含父」。

`RemoveChild` 的 `destroyAfterRemove` 默认为 `true`：移除后销毁这份引用。共享模板是否卸载，仍由模板上的存活拷贝数决定，不由某一个父节点单独决定。

## 11. 资源树

动态增删和递归嵌套把资源收成一棵树，称为 resource hierarchy。资源像积木，组合方式不能在框架里写死。项目过程中会加入坐骑、载具等新层级，例如：多个角色骑在坐骑上，角色（无论是否骑乘）再站到战车这类载具上；一个逻辑场景则包含场景资源、景物、角色、特效和渲染资源。框架只提供树的组合规则，不预知树上会有哪些节点。

结构规则：

- 内节点（非叶）都是 `ResourceGroup`，叶节点都不是 `ResourceGroup`。
- 成组资源的每个子资源都加载完毕，该成组资源才算加载完毕。
- 整棵树都加载完毕，才开始使用这棵树。该状态记为 `isHierarchyActive`。
- 叶节点完成时刻不同。每有一个叶节点加载完毕，就检查整棵树是否已经全部完毕。原文给出的检查代价是 O(N^2)，N 为节点数。
- `isHierarchyActive` 之前，对树的增删改只修改数据抽象，不把未齐套的结构应用到 `raw` 上。唯一的例外是叶节点首次接住自己的 raw 并开始生命期，它不建立任何联系，见 15.2。

推论：成组资源的子资源要么一起使用，要么一起不使用。使用或不使用任意一个子资源，就是使用或不使用整个成组资源；沿树递归，就是使用或不使用整棵 hierarchy。

这是逻辑激活的传播，不是所有权独占。子资源通过 `Reference` 被多处包含时，某一棵树停用，只释放这棵树持有的那份引用；模板上仍有其他拷贝时，模板继续存在。

从任意节点必须能找到整棵树（父链或等价结构）。原始资源到达时，刷新的是整棵树，不是孤立节点上保存的一段流程。

### 11.1 换装一类的中间状态

支持换装时，夏日套装正在使用，逻辑上已换成冬日套装，冬日资源尚未到齐。这一段里夏日资源是：

**已加载、仍在使用、逻辑上已经不被需要。**

数据抽象先变成冬日套装；冬日 hierarchy 尚未 `isHierarchyActive` 之前，夏日 `raw` 保持生命期，避免空窗。冬日到齐后，用 `ReplaceRaw`（以及成组资源上对应的整体替换）结束旧生命期、开始新生命期，再按新的 `data` 渲染。

因此有两类不同的「不要了」：


| 调用                                     | 含义                                    |
| -------------------------------------- | ------------------------------------- |
| `SetData` / `AddChild` / `RemoveChild` | 逻辑需求立即改变。旧 `raw` 可以留到新整体可用再替换         |
| `SetActive(false)`                     | 这份资源不再使用。打断加载，结束当前 `raw` 的生命期并 `Free` |


## 12. 状态与组合性

### 12.1 状态从哪里来

单个异步资源有三种加载状态：未加载、加载中、加载完毕。

成组并且「到齐才一起用」之后，还会出现：

- **已加载但未使用**：自己已经完成，仍在等关联资源。
- **已加载且已使用，但逻辑上不被需要**：换装过渡里仍显示着的旧套装。

树再支持每个节点增删改，如果每个需求变化都注册一段新 callback，这些状态会两两交错，组合成爆炸。

### 12.2 callback 为什么不能作为组合手段

`Load(Action<object> onLoadDone)` 这种 callback 代表一段写死的处理流程。资源树上每个节点的处理会变，节点之间的关系也在动态组合，固定流程表达不了这种变化。

新旧需求若各带一个 callback，底层无法知道它们是覆盖还是叠加，也就无法决定替换、保留还是排队。给 callback 分配 ID 再按 ID 取消，只是把决策退回上层，底层仍要处理「取消之后，加载中的资源或资源组怎么办」。

本框架的固定流程只有一条：持有整棵树，原始资源到达时按当前数据抽象刷新整棵树。需求变化改的是 `data` 和树结构，不是改一段待执行的 callback。

### 12.3 实现时要守住的不变量

1. 逻辑需求的每次变化都同步写入 `data` 或树结构，不依赖加载回调来补记需求。
2. `raw` 不在时，只改镜像；`raw` 到达、替换或 `data` 变化且当前可用时，用当时的完整 `data` 做 `Render`。
3. 生命期开始做初始化，结束做复原；期间的表现以 `data` 为准。
4. 成组资源可以更换多次 `raw`，叶节点不可以（只有 `null → raw` 与 `raw → null`）；同一次 `ReplaceRaw` 先结束后开始，同一对象替换自己则直接返回。
5. `SetActive(false)` 之后，进行中的加载被打断，迟到的 `raw` 不再进入生命期。
6. 成组资源的子节点全用或全不用；激活含义沿树传播到整棵 hierarchy。
7. 内节点是 `ResourceGroup`，叶节点不是。
8. `isHierarchyActive` 之前，结构变化只停留在数据抽象。
9. 父对子的包含通过 `Reference` 计数；增删子节点后，从本节点到根的数据抽象都换成新整体。
10. `AddChild` 拒绝会形成父子循环的插入。
11. 任意节点能定位整棵树；加载完成触发的是整树刷新。

## 13. 循环引用

引用计数会遇到循环引用，分三层处理：


| 层级                 | 处理                                                      |
| ------------------ | ------------------------------------------------------- |
| bundle             | 打包构建时消除循环依赖。做法见系列文《Unity3D-asset bundle划分优化》，不在本框架运行时处理 |
| asset 对 bundle 的计数 | 使用 asset 而增加 bundle 计数，方向是单向的，不构成环                      |
| 上层资源树，如角色系统        | `AddChild` 时检查，避免父包含子、子再包含父                             |


极端情况下若仍出现环：逻辑结构的修改是同步的，生命期调用不随加载时机变化，因此环是必现的，可以稳定复现后排查。这是确定性带来的结果。

## 14. 类型关系

```text
Resource
├── 叶子资源（如 AsyncGameObject）
│     Load / Free 对应一种具体来源
├── Clone
│   └── Reference          只拷贝模板地址
└── ResourceGroup
      children : Reference
      子节点可以再是 ResourceGroup 或叶子
```

模板用 `clones` 记住以它为模板的拷贝。成组资源的 `children` 里放的是 `Reference`，因此「包含」和「引用计数」是同一机制。

## 15. 实现规则

本节取代原先的「实现时仍可调整的细节」，把原文留给实现的流程定下来，并保持第 12.3 节的不变量。

15.2、15.3、15.4 是对流程的抽象，目前并不稳定，后续可能调整。调整流程时要守住 15.1 和 15.7：状态成员不增加，可推导量不落地成字段。

### 15.1 状态成员

```csharp
abstract class Resource
{
    protected object data;   // 全部使用信息
    protected object raw;    // 非空 ⟺ 生命期已开始
    bool active;             // 唯一的状态标志：逻辑需求
    Resource parent;         // 结构，不是状态
    HashSet<Clone> clones;   // 计数本身，见第 9 节

    protected abstract void Load(Action<object> onLoadDone);
    protected abstract void BreakLoad();
    protected abstract void Free(object raw);
    protected abstract void OnActive(object raw, bool active);
    protected abstract void Render(object raw);  // 镜像在派生类自己的字段里
}

class ResourceGroup : Resource
{
    HashSet<Resource> children;  // 逻辑构成，装的是 Reference
}

class Clone : Resource
{
    Resource template;           // 加载依赖
}
```

`active` 是唯一的状态标志。它留下来有两个理由：上层对根节点的需求没有别处可记；15.5 那条 `Free` 的式子要靠它区分「换一批子件」和「整组不要了」，而 `Free(object raw)` 的签名传不进这个信息。

其他状态一律查出来，见 15.7。每引入一个状态字段就要承担它与权威副本失同步的风险。资源树的任一节点在任一时刻都可能被增删改，这个风险不接受。

### 15.2 生命期开始，与装配分离

「原始资源到达」和「与兄弟建立联系」是两件事：

1. raw 到达即开始生命期 —— `OnActive(raw, true)` 随后 `Render(raw)` —— 前提是本节点当前没有与兄弟建立联系。这一步与兄弟无关，立即完成。
2. 已经建立过联系的节点不能就地换 raw。必须先拆散它与兄弟的联系，才能换、才能重建。
3. 拆散与重建由父资源执行，前提是父资源已加载完毕，即它的全部子节点都已就绪。
4. 重建改变了父资源的 raw。父资源若也已与它的兄弟建立联系，同一条规则递归上提，直到根。

因此第 12.1 节的「已加载但未使用」是 `raw` 非空而尚未装配，不是一个待提交的暂存结果。基类不需要暂存位。

两类节点对 raw 的替换权限不同：

| | 允许的 raw 变化 | 理由 |
| --- | --- | --- |
| 叶节点 | 只有 `null → raw` 和 `raw → null`，不允许 `raw1 → raw2` | 它的 raw 是外部交进来的、不可重算，必须当场接住；而它首次到达时父级没见过它的 raw，必然没有实际父级 |
| 成组资源 | 允许 `raw1 → raw2` | 它的 raw 是子资源集合，可以从 `children` 随时重算 |

成组资源替换 raw 的前提只有一条：**它的 raw 尚未与父资源和兄弟资源建立联系**，即没有实际父级，见 15.3。由此分出两种情形：

- **首次装配自下而上增量完成。** 某一级的子资源都加载完毕时，该级还没有任何联系，判据成立，就地装配。中间层的组会先于根完成装配，存在「中间层已装配而根未装配」的中间态。
- **换装一类的替换被迫上溯到根。** 从变动点到根的每一级都已建立联系，判据处处不成立，于是一路上传，最终在根上执行，再向下递归，见 15.4。

所以「上溯到根」不是规则本身，是稳定状态下判据的必然结果。规则只有「没有实际父级」这一条。

`IsLoaded()` 是虚方法：基类的默认实现是 `raw != null`，`ResourceGroup` 覆盖为「全部子资源都已加载完毕」，递归。第 11 节那个 \(O(N^2)\) 因此存在——每个加载结果到达都会触发若干次递归判定。效率问题统一留到全部设计完成之后再处理，不在设计阶段为它引入状态。

### 15.3 逻辑父级与实际父级

子资源有两种父级。两者都是查出来的，不存储。


|      | 判据                | 含义                                                  |
| ---- | ----------------- | --------------------------------------------------- |
| 逻辑父级 | `parent != null`  | 逻辑镜像上它属于这个成组资源。`AddChild` 置上，`RemoveChild` 清掉，同步、确定 |
| 实际父级 | 逻辑父级的 `raw` 包含本节点 | 它的原始资源已与兄弟建立联系，父资源的生命期已经把它纳入                        |


逻辑父级是向上报告的通路，也是上溯到根的通路。实际父级用于三处判断：

1. **加载结果到达时能否就地换 raw。** 有实际父级则不能，必须由父级先拆散联系，见 15.4。
2. `**RemoveChild` 是否当场收尾。** 无实际父级说明它从未建立联系，当场 `SetActive(false)`，连它已发起的加载一起回滚；有则留给重建时的 `Free`，否则第 11.1 节的空窗会回来。
3. `**BreakLoad` 回滚哪些子资源。** 无实际父级的那些才是本次 `Load` 拉起的。

### 15.4 重建由已有方法共同构成

没有单独的刷新驱动器，也没有 `Rebuild` 方法。资源树的处理由 `SetActive`、`Load`、`ReplaceRaw`、`OnActive`、`Free` 的实现共同构成，每个方法只按「当前的 raw 情况 + 当前的逻辑镜像」做本地决定。

成组资源的增删子资源，一律视为用新的一组子资源作为新的原始资源替换旧的。于是分成两件事：


|                            | 做什么                         |
| -------------------------- | --------------------------- |
| `AddChild` / `RemoveChild` | 只改逻辑镜像。不拉起加载，不触发任何重建        |
| `SetActive(true)`          | 批次提交点。一次性处理当前的逻辑镜像与实际的子资源集合 |


上层可以反复多次 `AddChild`、`RemoveChild`，期间什么都不会发生，然后调一次 `SetActive(true)`。因此框架不需要替上层缓冲批次，上层也不必关心增删的先后顺序。

`SetActive(true)` 不做「已 `active` 就返回」的判断，它总是发起 `Load`，由 `Load` 的幂等承担「同一使用周期内不重复加载」。

成组资源的 `Load` 只做一件事：对全部逻辑子资源递归 `SetActive(true)`，新加进来的由此被拉起。它不调 `onLoadDone`，也不存这个回调 —— 成组资源没有「加载结果到达」这个事件，第 6 节已经说明它的加载完毕是「每个子资源都已加载完毕」。它的 raw 不是被交付的，是从 `children` 算出来的，所以随时可以重算，不需要句柄，也不需要暂存。

#### 回溯：向上报告，在能装配的最低一级执行

每个节点在两种时机沿 `parent` 链向上报告：加载结果到达并就地装上之后，以及 `SetActive(true)` 之后。后者是必要的 —— 一个只做了 `RemoveChild` 的批次没有任何加载结果会到达，不报告就没人触发。

报告在每一级尝试装配，三个条件同时成立才执行：

> 没有实际父级，并且本子树已加载完毕，并且需要重建。

装配不成就继续上传；本子树尚未加载完毕则就地停住，因为它的父级必然也凑不齐子资源。首次装配因此在尽可能低的层级完成，换装则因为判据处处不成立而一路走到根。

「需要重建」要递归看整棵子树：换装时根自己的 `children` 并没有变，是它某个后代变了。而根交出的新集合即使与旧集合成员相同，也是一个新对象，所以 `ReplaceRaw` 不会早退，根的联系照样重建 —— 这是必须的，它的联系指向后代换掉的那些 raw。

装配的完整动作序列。中间两步在 `ReplaceRaw` 内部，首末两步由调用方补上 —— `ReplaceRaw` 只负责一次「结束旧的、开始新的」并把 `oldRaw` 交还出来，见前述实现：


| 步   | 位置             | 动作                                                                                                   |
| --- | -------------- | ---------------------------------------------------------------------------------------------------- |
| 1   | `ReplaceRaw` 内 | `OnActive(oldSet, false)` 拆掉本级联系。至此 `oldSet` 里的子资源都失去了实际父级                                           |
| 2   | `ReplaceRaw` 内 | `OnActive(newSet, true)`：建立联系之前，先让 `newSet` 里 raw 与自身逻辑镜像不一致的成组子资源各自 `ReplaceRaw`，递归展开同样这几步；然后建立本级联系 |
| 3   | 调用方            | `Free(oldSet)` 释放不再被需要的，需求是 `active ? children : ∅`                                                  |
| 4   | 调用方            | `Render(newSet)`                                                                                     |


第 2 步的递归下探就是两趟的来源：拆从父到子，建从子到父，严格嵌套。不需要额外驱动器，`OnActive` 的实现自己带出来。拆必须整趟先做完，因为父级建立的联系指向子级的旧 raw，让子级先换，父级再拆时引用已经失效。下探中每一级的 `ReplaceRaw` 返回的 `oldRaw`，由该级的调用点（即它父级的 `OnActive(newSet, true)`）负责 `Free`，与 15.5「谁供给 raw，谁负责回收换下来的那一份」一致。

`Free` 晚于本级的拆，这是销毁的安全条件：被 `Free` 的那些 raw 在第 1 步里已经失去上层联系，销毁时不会有谁还指着它。它们也必然不在 `newSet` 里，所以排在建之后同样安全。

首次装配是这条流程的退化情形：该级的 `oldSet` 为空，第 1、2 步跳过，第 3 步里的下探也一无所获（子组早已各自装配好），只剩建立本级联系和刷新。下探只为换装一类的重建存在。


| 入口                                      | 动作                                                                                  |
| --------------------------------------- | ----------------------------------------------------------------------------------- |
| `SetActive(bool on)`                    | 取 `GetHierarchyRoot().IsLoaded()` 作为 `isHierarchyLoaded`，转调下一行                      |
| `SetActive(on, isHierarchyLoaded)` 的真分支 | `active = true`；`Load()`；`raw` 非空则 `Render(raw)` 提交本级镜像；向上报告。`isHierarchyLoaded` 为假时可截断报告，整树凑不齐，装配必然不成 |
| 同上的假分支                                  | `active = false`；`BreakLoad()`；`var oldRaw = ReplaceRaw(null)`；`oldRaw` 非空则 `Free` 它 |
| `SetData` 及派生类的 setter                  | 只改镜像。不加载、不触发生命期、不 `Render`。生效由后续的 `SetActive(true)` 统一提交                            |
| `AddChild` / `RemoveChild`              | 只改 `children` 与 `parent`。`RemoveChild` 的 `destroyAfterRemove` 见 15.8                 |
| `OnLoadDone`                            | `active` 为假则收尾掉这份结果并返回；无实际父级则就地 `ReplaceRaw`、`Render`；向上报告                          |


假分支的三条语句覆盖了原文列的三支：未加载时 `BreakLoad` 是空操作、`ReplaceRaw(null)` 返回 null；加载中时 `BreakLoad` 终止加载并回滚它的副作用，`ReplaceRaw(null)` 同样返回 null；已加载时 `BreakLoad` 是空操作，`ReplaceRaw(null)` 走 `OnActive(raw, false)` 并交回旧 raw 去 `Free`。不需要分支判断。

### 15.5 成组资源的 raw

成组资源的 raw 是「已建立联系的那一组子引用」在上次装配时刻的快照。四个抽象方法因此有确定含义：


| 方法                        | 含义                                     |
| ------------------------- | -------------------------------------- |
| `OnActive(linked, true)`  | 建立 `linked` 里各子资源之间的联系。此时各子节点的 raw 已就位 |
| `OnActive(linked, false)` | 把这些联系拆开                                |
| `Free(linked)`            | 归还这一批引用中不再需要的部分                        |
| `Render(linked)`          | 组自身 `data` 对这一组的作用                     |


`Free` 只有一条式子：

> `Free(old)` 释放 `old` 减去当前需求的部分，当前需求是 `active ? children : ∅`。

换一批子件和整组停用走同一条式子。前者 `active` 为真，差集是被移除的那些；后者 `active` 已为假，差集是全部。

成组资源的刷新不快照 `children`，只读当前的 `children`，这正是第 4 节「只读 data，不依赖历史上某次调用残留的参数」。加进来的子节点参与就绪判定，移走的退出判定。装配过程是同步的、不可重入的，中途没有外部调用插进来。

### 15.6 派生类的义务


| 义务                           | 说明                                                                    |
| ---------------------------- | --------------------------------------------------------------------- |
| `Load` 幂等                    | 已发起且未结束时再次调用不重复加载。进行中的句柄就是「正在加载」这个状态，基类不另存标志                          |
| `BreakLoad` 回滚 `Load` 的全部副作用 | 终止进行中的加载，并把 `Load` 做过的事退回去，使本节点回到未加载。尚未开始或已经完成时什么都不做。基类据此不必记录加载进行到哪一步 |
| 丢弃被打断的结果                     | 底层无法取消 IO 时，在完成回调里判别句柄并把结果收尾掉，见第 7 节                                  |
| 清句柄早于交出结果                    | 把结果交给基类之前先清掉自己的加载句柄。回调可能同步跑完整个刷新，并在其中再次 `SetActive`                   |


基类对迟到结果只做一道兜底：`active` 为假就把它 `Free` 掉。per-load 的身份判别放在派生类，它手上有句柄，判别是免费的。

`SetActive(false)` 紧跟 `SetActive(true)`、而旧结果先于新结果到达，是派生类必须靠句柄判别挡住的情形。基类那道 `active` 兜底在这里不生效（`active` 已经重新为真），而 15.2 禁止叶节点 `raw1 → raw2`，所以两份结果都装上会直接违反不变量。这是把身份判别放在派生类的硬理由，不只是效率考虑。

### 15.7 可推导量

以下都不存储。每一个的权威副本都已经记在别处。


| 量                   | 推导                                                  |
| ------------------- | --------------------------------------------------- |
| 逻辑父级                | `parent`                                            |
| 实际父级                | `parent != null` 且 `parent` 的 `raw` 包含本节点，见 15.3    |
| 是否正在加载              | 派生类的加载句柄。成组资源没有句柄，见 15.4                            |
| 是否是根                | `parent == null`                                    |
| `isHierarchyActive` | `parent == null && raw != null`                     |
| 加载完毕                | `IsLoaded()`，虚方法。基类 `raw != null`；`ResourceGroup` 覆盖为全部 `children` 递归加载完毕 |
| 需要重建                | 本节点的 `raw` 集合与 `children` 不一致，或任一成组子资源需要重建          |
| 已移除但仍在显示的子引用        | 组的 `raw` 减 `children`                               |
| 引用计数                | `clones` 的大小                                        |


### 15.8 包含、计数与移除

约定：想直接使用一份资源，就对它取一份 `Clone` 或 `Reference`。不要让同一个句柄既被直接使用、又同时充当别人的模板。这样 `clones` 就是完整且唯一的计数，`clones` 空了即可无条件结束模板的使用，不必再给「被上层直接驱动」另设标志。

`RemoveChild` 的两个分支对框架是同一个动作：销毁组自己那份引用，模板计数减一。子资源能否继续存活由 `clones` 是否已空决定，与哪个父节点移除了它无关。要让子资源在移除后继续存活，在移除前对它另取一份引用。`destroyAfterRemove` 因此只表达意图，不需要对应的状态，也不需要在装配时分支。

第 10.2 节的 `AddChild` 里写死了 `new Reference(newChild)`，但第 9 节那张表说明拷贝方式随资源而不同：prefab 要整份实例化，texture 只拷地址。写死成 `Reference` 时，一份 prefab 类资源被两个组包含会得到同一个引擎对象，两个组的 `OnActive` 会互相覆盖对它的挂接。所以 `AddChild` 应当向子资源索取一份拷贝，由子资源决定拷贝方式，默认是 `Reference`。

环检查要沿 `children` 和 `template` 两条依赖边求新子节点的依赖闭包，看是否包含 `this`。只检查父链和 `children` 下行会漏掉经由模板构成的环。

### 15.9 仍然开放

1. **第 8 节的篮球例子。** 它是对一个叶子级资源做 `raw1 → raw2`（红球 `0x1234` 换成 `0x5678`），而 15.2 已经禁止叶节点换 raw。自洽的表达是把它提到父组一级：父组移除旧球资源、加入新球资源，旧球的生命期在重建时的 `Free` 差集里结束，新球按当前 `data` 染成红色。这样「替换原始资源」只发生在成组资源上，叶子与 raw 一对一。采用这个表达要改第 8 节的叙述。未定。
2. **外部对成组资源调 `ReplaceRaw` 而判据不成立。** 叶节点已经禁止换 raw，所以这一条只剩成组资源：上层直接交进来一个新集合，而该节点此刻有实际父级，替换不能执行。这份新 raw 的归属属于上层，框架不收留它。未定的只是这时该返回失败、还是断言。
3. **加载失败。** 失败的节点永远不加载完毕，整棵树永远装配不了。重试、占位、整树降级都不在第 1–14 节里。未定。
4. **成组资源对父级的挂接代表。** 成组资源的 raw 是一组子引用，没有单一的引擎对象。父级建立联系时需要一个可挂接的对象，否则必须下探到子组的叶子。合理的做法是在引擎层派生一种成组资源，装配时额外建一个空物体当挂点，把自己的子件挂到它下面，父级只挂这个空物体 —— 即第 4 节那个「先放一个空物体」的推广。`Base.Res.ResourceGroup` 不涉及引擎对象，这一层留给 `Engine`。未定。
